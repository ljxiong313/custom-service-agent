# 平台接入指南（P7）

本文档记录四大电商平台（淘宝/天猫、京东、拼多多、抖店）接入本系统智能客服所需的
**全部 webhook、API 与配置参数**，以及每一项参数去哪里获取、哪些需要接入前核对。
代码位置：`src/backend/app/services/platforms/`（base/adapters/inbound）、
`src/backend/app/api/v1/platforms.py`（回调与管理端点）。

> ⚠️ 诚实声明：各开放平台的网关地址、消息类 API 方法名与系统参数**版本迭代频繁**。
> 本文中标注 ★ 的条目是按公开文档口径填写的占位/参考值，**填入真实凭证前必须逐项
> 对照当时的官方文档核实**，必要时只需改配置（gateway/reply_method/字段名均可覆盖），
> 不必改代码。mock 模式（默认）不依赖任何一项真实参数即可演示全链路。

## 1. 总体架构

```
平台买家发消息
   │  （平台服务器 HTTP 推送 / TMC 长连接桥接）
   ▼
POST /api/platform/{platform}/callback     ← 免 JWT；验签 → 解析 → 快速 ack
   │  BackgroundTasks 异步处理（平台推送普遍有 3~5s 超时重试）
   ▼
handle_inbound(InboundMessage)
   │  ensure_external_conversation：按 (platform, shop_id, buyer_id)
   │  找/建「影子用户 + 影子会话」（ExternalConversation 映射表）
   ▼
runner.run_turn(interactive=False)          ← 与网页端同一轮次实现：
   │  RAG/商品/记忆工具、转人工关键词、挂起状态机全部生效；
   │  MCP 需确认类工具在平台渠道直接按拒绝处理（无人可点确认卡片）
   ▼
adapter.send_reply(shop_id, buyer_id, 回复文本)
   │  mock=true → 写入外发箱表 outboxrecord（GET /api/v1/platforms/outbox 可查，重启不丢）
   │  mock=false → 按各平台签名规则调用消息发送 API
   ▼
买家在平台客户端（千牛/飞鸽/京麦/拼多多商家版）看到回复

转人工后：人工客服在网页工作台回复（POST /api/v1/handoff/tickets/{id}/reply）
   → staff_reply 落库会话 → push_staff_reply 查 ExternalConversation
   → 同一 adapter.send_reply 送达平台买家。网页会话不触发外发。
```

设计要点：

- **单一会话中枢**：所有渠道（网页、四平台、企微客服侧）都投影到内部
  `Conversation/Message` 模型上，Agent 能力（RAG、记忆、转人工）只写一遍。
- **影子用户不可登录**：username 为 `pl_<md5(platform:shop:buyer)[:20]>`，
  密码为随机 uuid4，仅承载消息与长期记忆归属。
- **快速 ack + 后台处理**：回调端点验签后立即返回平台要求的应答体，重活交给
  BackgroundTasks；重复推送由 `inbound.claim_message` 按 (platform, shop_id, buyer_id, msg_id) 幂等丢弃（表 `inbounddedupe`，平台未给 msg_id 时不去重）。
- **运营可主动开单**：买家一直不回复"是"（确认式转人工停在 `awaiting_confirm`）时，运营台
  可对任意渠道会话手动建单（`POST /api/v1/handoff/tickets`，工作台「手动建单」）——工单归属记
  会话的真实主人（影子买家），企微卡片才显示对的人名；已终结会话一律 409，同一会话有未结单则复用。

## 2. 配置总览

配置节：`platforms.<name>`（`config.simple.yaml` 有全量注释模板；
`config.local.yaml` 是本地覆盖——**注意 CS_CONFIG 是整文件替换而非合并**，
使用 config.local.yaml 启动时该文件必须自带 platforms 节）。

| 字段 | 类型 | 说明 |
|---|---|---|
| `enabled` | bool | 渠道总闸：false 时回调一律 409（连验签都不做）；未注册的平台名恒 404。状态页恒列四平台，enabled 作为字段回显 |
| `mock` | bool | **默认 true**。true：验签放行、回复写入外发箱表 `outboxrecord`（B1-2 起落库，重启不丢）；false：真实签名外呼 |
| `app_key` | str | 平台应用凭证（拼多多语义为 client_id） |
| `app_secret` | str | 签名密钥，绝不出现在任何接口回显中 |
| `access_token` | str | 卖家授权令牌（京东/拼多多系统参数名即 access_token） |
| `session_key` | str | 仅淘宝备选字段：TOP 授权后的 session，与 access_token 二选一 |
| `gateway` | str | 消息发送 API 网关地址（已按公开文档预填，★核对） |
| `reply_method` | str | ★ 客服消息发送 API 的方法名/路径，必填才能真实外呼 |
| `callback_verify` | str | `"sign"`=按各平台算法验签；`"none"`=跳过（仅限本地调试） |
| `to_uid_field` / `content_field` | str | 回复业务参数中"收件买家/消息内容"的字段名（★核对） |
| `media_method` | str | ★ 媒体消息发送 API 的方法名/路径；留空时图片/文件降级为"[附件] 名称+URL"文本 |
| `media_url_field` / `media_type_field` | str | 媒体回复参数里"地址/类型"的字段名（★核对） |
| `ack` | dict/str | 回调即时应答体，各平台要求不同（见各节） |

管理接口（JWT 保护，前端 Settings 页与冒烟脚本使用）：

- `GET /api/v1/platforms/status` — 各平台 enabled/mock/has_credentials/gateway/会话数（只回布尔，不回显任何密钥）
- `GET /api/v1/platforms/readiness` — 逐平台**就绪自检**：入站/出站/媒体三条链路
  各缺哪些配置项，`ready_in`/`ready_out`/`ready_media` 分别判定；缺项直接给出该填的字段名，
  避免"配了一半就发不出去"要靠读代码定位
- `GET /api/v1/platforms/outbox` — mock 模式各平台外发记录（演示"回复已送达买家"；
  数据在 `outboxrecord` 表，重启后仍可查）

回调端点（免 JWT，供平台服务器直连，需公网 HTTPS）：

- `POST /api/platform/taobao/callback`
- `POST /api/platform/jd/callback`
- `POST /api/platform/pdd/callback`
- `POST /api/platform/douyin/callback`

## 3. 淘宝 / 天猫（TOP + TMC）

**入驻**：淘宝开放平台 open.taobao.com → 创建应用。客服消息类能力通常要求
「商家自研」或「服务商（ISV）」身份并订购对应权限包（如"淘宝客/旺信/客服消息"
权限组，名称随平台调整 ★），且需卖家对应用授权（获得 session）。

**入站（重要差异）**：淘宝买家消息的官方通道是 **TMC 消息服务**（WebSocket 长
连接，需运行官方 SDK 进程），**不是普通 HTTP 回调**。本系统的
`/api/platform/taobao/callback` 承接的是 mock 推送与兼容形态（HTTP JSON）。
真连方案二选一：
1. 部署一个 TMC SDK 桥接进程，收到消息后转发（HTTP POST）到本回调端点；
2. 若应用获批 HTTP 推送形态，直接在开放平台后台配置回调 URL。

**签名（TOP 通用，MD5 口径）**：

```
sign = MD5( app_secret + 按 key 字典序拼接(k1v1k2v2…) + app_secret ).hexdigest().upper()
（sign_method=hmac-md5 变体存在，★ 按应用配置核对）
```

**出站系统参数**（form 提交到 gateway）：

| 参数 | 值 |
|---|---|
| method | `reply_method`（★ 如客服消息发送 API 名，示例占位 `taobao.wangwang.eservice...` 类，必须核对） |
| app_key | 应用 AppKey |
| session | access_token/session_key（卖家授权令牌） |
| timestamp | `yyyy-MM-dd HH:mm:ss` |
| format | json |
| v | 2.0 |
| sign_method | md5 |
| sign | 上式计算 |

**入站消息解析字段**（body JSON，键名大小写不敏感）：
买家 `buyer_id`/`buyer_nick`/`uid`；文本 `text`/`content`/`msg`；店铺 `shop_id`/`shopId`/`store_id`。

**ack**：`{"code":0,"msg":"success"}`（HTTP 200 即视为成功；桥接模式下 ack 无强制口径）。

**mock 演示命令**（PowerShell/Git Bash 均可）：

```bash
curl -X POST http://127.0.0.1:7861/api/platform/taobao/callback \
  -H "Content-Type: application/json" \
  -d '{"shop_id":"shop_demo","buyer_id":"buyer001","text":"这个面霜敏感肌能用吗","msg_id":"m1"}'
```

## 4. 京东（京麦 / 宙斯开放平台）

**入驻**：京东开放平台 open.jd.com（商家自研走"服务市场-商家自研"通道 ★）。
客服消息权限需申请对应 API 权限包；授权卖家店铺后获得 access_token。

**回调 URL**：平台后台"消息推送服务"中配置
`https://<你的域名>/api/platform/jd/callback`，选择 JMQ/HTTP 推送形态（★ 核对）。

**签名**：与 TOP 同族 MD5 拼串（`app_secret` 包裹排序拼串，大写 hex）。
**系统参数差异**：用 `access_token` 而非 `session`：

| 参数 | 值 |
|---|---|
| method | `reply_method`（★ 如 `pop.waybill...`/客服消息发送类 API，核对） |
| app_key / access_token / timestamp / format=json / v=2.0 / sign_method=md5 / sign | 同 TOP 口径 |

**入站解析字段**：买家 `buyer_pin`/`buyer_id`/`open_id`；其余同公共口径。
**ack**：`{"code":0,"msg":"success"}`。

```bash
curl -X POST http://127.0.0.1:7861/api/platform/jd/callback \
  -H "Content-Type: application/json" \
  -d '{"shop_id":"jshop1","buyer_pin":"jd_user_88","text":"订单什么时候发货","msg_id":"j1"}'
```

## 5. 拼多多（开放平台）

**入驻**：拼多多商家开放平台 im.open.pinduoduo.com → 创建应用（商家自用型即可
获取客服消息能力 ★核对资质要求），授权店铺后获得 access_token。

**回调 URL**：应用详情"消息推送"配置
`https://<你的域名>/api/platform/pdd/callback`。

**签名**：TOP 同族 MD5（`client_id` 语义即 app_key）。**系统参数差异**：

| 参数 | 值 |
|---|---|
| type | `reply_method`（★ 如 `pdd.chat...`/消息发送类 API，核对） |
| client_id | app_key |
| access_token | 授权令牌 |
| timestamp | **秒级整数**（字符串） |
| response_type | json |
| sign | MD5 拼串大写 |

**入站解析字段**：买家 `uid`/`buyer_uid`/`buyer_id`；文本 `text`/`content`/`msg`。
**ack**：拼多多要求响应体含 `error` 结构，配置预填 `{"error":{}}`（成功语义 ★ 核对）。

```bash
curl -X POST http://127.0.0.1:7861/api/platform/pdd/callback \
  -H "Content-Type: application/json" \
  -d '{"shop_id":"pddshop","uid":"pdd_buyer_7","text":"转人工","msg_id":"p1"}'
```

## 6. 抖店 / 飞鸽（巨量商家开放平台）

**入驻**：抖店开放平台 op.jinritemai.com → 创建应用；客服消息（飞鸽）能力
需相应权限包与店铺授权，获得 app_key/app_secret/access_token。

**回调 URL**：应用"消息接收"配置 `https://<你的域名>/api/platform/douyin/callback`。

**验签**：公开口径多版本并存，代码默认实现为
`sign = HMAC-SHA256( app_secret, timestamp + 原始body ).hexdigest()`，
取 header `x-doudian-sign` 或 query `sign` 比对（★ 若平台实际为 query 参数 md5
拼串口径，改 callback_verify 或按文档微调 verify_signature）。

**出站**：JSON POST 到 `gateway + method`，body 即系统参数全集：

| 参数 | 值 |
|---|---|
| app_key / access_token / timestamp(秒) / v="2" / sign_method="hmac-sha256" | |
| method | `reply_method`（★ 飞鸽客服消息发送 API 路径，如 `im.send...` 类，核对） |
| param_json | 业务参数**紧凑 JSON**（ensure_ascii=False、无多余空格，参与签名） |
| sign | `HMAC-SHA256(app_secret, app_key+timestamp+method+param_json+access_token)` |

**入站解析**：消息体优先取 `data` 嵌套层；买家 `uid`/`buyer_id`/`sender_id`/`open_id`；
文本 `content`/`text`/`msg`。**ack**：`{"code":0,"msg":"success"}`。

```bash
curl -X POST http://127.0.0.1:7861/api/platform/douyin/callback \
  -H "Content-Type: application/json" \
  -d '{"data":{"shop_id":"dyshop","uid":"dy_buyer_1","content":"有优惠券吗","msg_id":"d1"}}'
```

## 7. 切换真实对接 checklist

1. 拿到某平台凭证 → `config.local.yaml` 对应 `platforms.<name>` 填
   `app_key/app_secret/access_token`，`mock: false`；
2. 核对并填 `gateway`、`reply_method`、`to_uid_field`、`content_field`、`ack`（★ 项）；
3. 服务器具备**公网 HTTPS** 域名（平台回调普遍拒绝 http/裸 IP），在平台后台配置
   `https://<域名>/api/platform/<platform>/callback`；
4. 淘宝如需真收买家消息，另起 TMC SDK 桥接进程转发到回调端点（见 §3）；
5. 冒烟：用平台"消息调试/沙箱"功能或等待真实买家消息，观察
   `GET /api/v1/platforms/status` 会话数与后端日志 `平台会话建档`；
6. 失败排查：验签失败（403）→ 对照 §3~§6 签名口径与 `callback_verify`；
   发送失败（日志 `回复发送失败`）→ 打印 RuntimeError 提示的缺失参数名。

## 8. 与转人工（P3/P8）的关系

- 平台会话命中转人工（关键词/模型判定）后进入 **P8 两步制**：Agent 先经平台出站询问买家
  "是否需要转接人工客服"，买家回复肯定（"是/好的/需要…"）才建工单 + 企微卡片提醒客服；
  否定或答非所问则回 bot 继续智能接待；
- 排队/人工服务期间机器人挂起、买家侧只会收到"已为您联系人工客服"类提示
  （该提示同样经平台出站送达）；
- 客服在工作台或会话运营台回复 → 自动经 `push_staff_reply`/`deliver_notice` 送达买家所在平台；
- 会话空闲超时（P8）：结束提示与终结语也经平台出站送达买家，超时终结会强制关闭未结工单；
- **平台原生转接**（千牛转人工、飞鸽坐席分配）发生在平台侧，不经过本系统——
  若店铺同时启用了原生人工，两边消息会并行，建议接入后关闭平台侧自动分流或在
  平台侧仅挂本应用为唯一接待方（★ 各平台接待模式配置方式不同，核对）。

## 9. 已知限制

- 消息类型目前只处理**纯文本**；图片/商品卡片/订单卡片消息 parse_message 返回 None（丢弃并 ack），待扩展；
- 运营台可发送图片/文件给买家，但**平台出站默认仅有文本通道**：附件以"[附件] 名称+URL"文本形式
  随消息送达（`media_method` 留空即此降级；真实送达需填各平台媒体上传 API 与
  `media_url_field`/`media_type_field` ★，mock 外发箱完整记录 attachments 结构）；
- 已做平台消息 `msg_id` 幂等去重（表 `inbounddedupe`，键为 platform+shop_id+buyer_id+msg_id）；
  平台不给 msg_id 的消息无法去重，重复推送仍可能重复应答；
- 会话被空闲超时终结后买家再来咨询，会在同一影子用户下**自动开新一轮会话**（旧会话保留完整历史，
  ExternalConversation 每轮一条，运营台两轮都可见）；
- 未做发送侧限频/合规退避（平台对客服消息有频控 ★）；
- 淘宝 TMC 桥接进程未实现（文档口径已给，属部署项而非编码阻塞）；
- mock 外发箱自 B1-2 起落库（表 `outboxrecord`），重启不丢、`/platforms/readiness` 能按渠道
  计数；但它记的是"我们决定发什么"，**不是平台送达回执**，别当审计日志用。
