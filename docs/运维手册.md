# 运维手册

> 面向"把这套系统交到别人手上跑生产"的人。安全口径见 docs/待办与风险.md，
> 功能能力见 README.md，架构分层见 docs/项目结构说明.md，
> **多店交付物与逐条上线命令在 [`deploy/README.md`](../deploy/README.md)**。
> 本手册只写**怎么部署、怎么确认它是健康的、出事怎么办**。

## 1. 部署形态选择

| 形态 | 适用 | 配置要点 |
|---|---|---|
| 单容器（推荐起步） | ≤ 50 并发会话、单机、一个店 | `docker compose up -d`；前端产物由后端同源托管（`CS_SERVE_FRONTEND=true`），`CS_CORS_ORIGINS` 留空 |
| 多店（**一店一套实例**） | 多个互不相关的店铺同时接入 | `deploy/docker-compose.shop.yml` + `deploy/shop.example.yaml` + `deploy/env.shop.example`；每店一个库、一套向量目录、一个域名 |
| 多副本 | 需要 >1 进程 | 数据库必须换 Postgres/MySQL；`CS_SERVER_WORKERS` 或 compose `scale`；限流阈值按副本数折算 |
| 开发 | 本机联调 | `cd src/backend && py run.py` + `cd src/frontend && npm run dev`（8091 代理 /api 到 7861） |

多副本为什么可以：MCP 工具确认、记忆管道任务都落了库（`toolconfirmrequest` /
`memoryjob`），生命周期扫描、记忆补跑、出站重试都靠 `workerlease` 表做租约选主——
同一时刻只有一个进程真正在动手，持约进程挂掉后别的实例在一个 TTL（90~180s）内接管。

每进程仍各有一份的东西（不影响正确性，只影响效率与计数精度）：

- BM25 索引缓存与 Chroma collection 句柄（`app/services/rag/`）
- MCP 工具发现缓存（30s TTL，`app/services/mcp/manager.py`）
- 限流令牌桶（`app/utils/rate_limit.py`）——**阈值要除以副本数**，否则整体放行量翻倍
- `/metrics` 里的 `cs_http_requests_*` 是进程计数，抓取端需要按实例聚合（Prometheus 的
  `sum by ()` 或 federation）

### 1.1 多店 = 多套实例（结论与依据）

**结论**：接第二个店的时候，不要试图让一个实例服务两个店。正确形状是一店一套
"容器 + 数据库 + 向量目录 + 域名"，共享的只有镜像和反代。交付物在
[`deploy/`](../deploy/README.md)：`shop.example.yaml`（一店一份配置）、
`env.shop.example`（一店一份密钥）、`docker-compose.shop.yml`（一店一段 service）、
`nginx.shop.conf`（一店一个 server 块，含 SSE 关缓冲）、`cs-agent@.service` 与
`cs-backup@.*`（裸机形态与每店快照）。

**为什么不是配置问题而是数据模型问题**，三条代码依据：

1. **平台凭证按平台整节读取，一个平台只有一套 token**。
   [app/services/platforms/base.py:72](../src/backend/app/services/platforms/base.py#L72)
   读的是 `platforms.<name>` 这一节的 `app_key/app_secret/access_token`，而 TOP session、
   京东 access_token 是**按店铺授权**的。同平台两个店共用一套 token 的后果不是报错，
   是回复发错店——买家在 A 店问的问题，答案从 B 店的授权发出去。
2. **知识库与商品表没有 shop 维度**。
   [app/db/models.py:108、:137](../src/backend/app/db/models.py#L108)
   的 `KnowledgeFile` / `Product`（以及由它们派生的 `Chunk`）都没有 `shop_id` 字段，
   检索是全库召回。一个实例接两店 = A 店的退货政策会被召回给 B 店的买家，
   而且模型会把这段上下文当成正确答案说出来。§10 里"多租户没有"说的就是这件事。
3. **Chroma 是本地目录 + 进程内单句柄**。
   [app/services/rag/vectorstore.py:62](../src/backend/app/services/rag/vectorstore.py#L62)
   用 `lru_cache(maxsize=1)` 缓存按路径打开的 `PersistentClient`（同文件 :74 打开目录）。
   跨进程/跨机共用同一个目录没有验证过，属于"能跑但随时可能撕裂索引"的状态。

**每店必须不同的四样**（`deploy/shop.example.yaml` 抬头也标了同样的四项）：

| 项 | 在哪配 | 忘了会怎样 |
|---|---|---|
| 数据库 | `database.url` ← `CS_DB_NAME` | 两店共用一个库：数据互相覆盖，且备份/恢复没法按店走 |
| 向量目录 | `rag.chroma_path` + `rag.bm25_index_path` | 两店共用一个 chroma 目录：向量互相污染 + 写者冲突 |
| 域名 | `server.public_base_url` ← `CS_PUBLIC_BASE_URL` | 附件与回访链接串店；有真实外呼却没配它，生产直接拒绝启动 |
| 密钥 | `CS_JWT_SECRET` 等（每店重新生成） | 一把钥匙开所有店：单点泄漏变成全店登录态泄漏 |

顺带收益：`agent` 那一节（店名、禁语、发货口径、转人工话术）本来就每店不一样，
一店一份配置正好把它隔开，换商家不动代码。

**同店扩容不是加店**。同一个店要 >1 进程时，`CS_SERVER_WORKERS>1` 只在 Postgres 前提下可用，
并且要一起承担：限流阈值按进程数折算、BM25/工具发现缓存每进程一份、
Chroma 句柄在进程内（同店多进程共用一个 `chroma_path` 同样未验证）。
更稳的做法是给这个店再起一个实例（独立端口 + 独立 `chroma_path`，nginx 加权），
也就是把"多店"的那套形状复用成"一店多实例"。租约选主（`workerlease`）保证扫描与重试不会重复执行。

依赖上有一条连带变化：Postgres 驱动 `psycopg[binary]` 已经进 `src/backend/requirements.txt`。
只用 SQLite 时用不到它，但镜像要能跑生产那一档；自己精简依赖把这条删了，
换 Postgres 的第一个症状是启动即报 `No module named 'psycopg'`。MySQL 另需 `pymysql>=1.1,<2.0`，
默认没装。

## 2. 配置与密钥注入

优先级：环境变量 > `CS_CONFIG` 指向的 YAML > `config.simple.yaml`。

配置文件里任何字符串值可以写 `${VAR}` 或 `${VAR:-默认值}` 引用环境变量，所以密钥
不必落在文件里：

```yaml
security:
  jwt_secret: ${CS_JWT_SECRET}
multi_models:
  dashscope:
    api_key: ${CS_MODEL_API_KEY}
```

容器/编排层直接用的覆盖键（完整表见 `app/config.py` 的 `ENV_OVERRIDES`）：

| 环境变量 | 落到 | 说明 |
|---|---|---|
| `CS_SERVER_ENV` | `server.env` | `production` 打开安全硬闸（见 §3） |
| `CS_JWT_SECRET` | `security.jwt_secret` | ≥32 位随机串；`openssl rand -hex 32` |
| `CS_MODEL_API_KEY` | `multi_models.<default_model>.api_key` | 只作用于默认 provider |
| `CS_PUBLIC_BASE_URL` | `server.public_base_url` | 平台买家点开附件链接的公网地址，末尾不带 `/` |
| `CS_CORS_ORIGINS` | `server.cors_origins` | 逗号分隔；同源部署留空 |
| `CS_SERVE_FRONTEND` | `server.serve_frontend` | 后端直接托管 dist |
| `CS_SERVER_WORKERS` | `server.workers` | 进程数 |
| `CS_DB_URL` | `database.url` | 换库 |
| `CS_METRICS_TOKEN` | `security.metrics_token` | `/metrics` 的访问令牌 |

**红线**：`config.local.yaml` 与 `data/`（含备份快照）都已在 `.gitignore`/`.dockerignore`
里挡住，别为了省事把它们拷进镜像层或提交上去。备份快照里带着同名配置文件，等于带密钥。
多店形态的真实配置落在 `deploy/etc/`、`deploy/env/`、`deploy/data/`，同样按目录挡在
`.gitignore` 里——那份目录里只允许 `*.example` 模板入库。

**插值只认两种写法**：`${VAR}` 与 `${VAR:-默认值}`（`app/config.py` 的 `_ENV_REF`）。
shell/compose 的 `${VAR:?说明}` 在这里**不会**被替换，后果是这串字符原样进配置——
最典型的是把 DSN 写坏，然后连不上库 yet 日志里没有插值错误可看。要表达"这个必填"，
用哨兵默认值（如 `${CS_DB_NAME:-SET_CS_DB_NAME_PER_SHOP}`，漏配就去连一个不存在的库、
启动即失败），或直接留空让 §3 的硬闸拦下（如 `jwt_secret`）。多店模板见
[`deploy/shop.example.yaml`](../deploy/shop.example.yaml) 与 [`deploy/env.shop.example`](../deploy/env.shop.example)。

## 3. 生产形态的硬闸

`server.env=production` 时这些会变成"拒绝启动 / 拒绝请求"，不是警告：

| 项 | 行为 | 位置 |
|---|---|---|
| `jwt_secret` 是默认值或 <32 位 | 启动失败 | `app/startup_check.py` |
| 启用的平台 `callback_verify=none` | 启动失败；请求期验签直接判负 | `startup_check.py`、`platforms/base.allow_none_verify()` |
| CORS 含 `*` | 启动失败 | `startup_check.py` |
| 自助注册 | 默认关闭（空库自举除外） | `api/v1/auth._registration_open()` |
| `npx/uvx/uv` 作为 MCP stdio 命令 | 拒绝登记/连接 | `mcp/manager._package_runners_allowed()` |
| MCP sse/http 端点指向内网/链路本地地址 | 拒绝登记（SSRF 面） | `mcp/manager.validate_url()` |
| 未配 `metrics_token` | `/metrics` 返回 403 | `app/main.py` |

这些项同时出现在 `GET /api/v1/system/alerts` 与 `/ready`，不用翻日志。

## 4. 上线前 checklist（按顺序做）

> 多店形态下，**这份 checklist 是"每店各跑一遍"**，不是"整体跑一遍"：密钥、库、向量目录、
> 平台授权都按店独立。部署动作本身的顺序在
> [`deploy/README.md`](../deploy/README.md)（建库 → 每店配置与密钥 → 起容器 → `/ready` → 反代 →
> 自举 admin → 逐平台灰度）。

1. `python -m pytest -q`、`ruff check src eval`、`mypy`、前端 `npm run typecheck && npm run test && npm run build` 全绿（CI 已串好，见 `.github/workflows/ci.yml`）。
2. `python scripts/ci_smoke.py`——它会临时起一个隔离实例跑端到端三套脚本（45/29/9 项）。
   有真模型 key 时把 `CS_MODEL_API_KEY` 注进去，评测里的对话断言就不会 SKIP。
3. 首次部署（空库）：用注册页开第一个账号 → 它自动是 admin → 在设置页给客服开 `staff` 账号。
   生产关闭了自助注册，别在上线当天才发现"招不到客服"。
4. 配 `CS_PUBLIC_BASE_URL`（否则买家在平台里收到 `[附件] xxx: /api/files/...` 点不开）。
5. 逐平台把 `mock` 改 false、`callback_verify` 改回 `sign`，按 docs/平台接入.md 核对参数名。
6. 决定要不要开**满意度回访**（`session.rate_survey_enabled`）：开了以后结单告别语会带上
   一条评价链接，属于对买家可见的外发内容，话术要业务方定稿；没配 `CS_PUBLIC_BASE_URL`
   时链接是相对路径、买家点不开，所以真实外发下它属于启动自检的 fatal 项。
7. 跑一次**备份 + 恢复演练**（§6），并把时间记录在交付单里。没演练过的备份不算备份。
8. 确认抓取端已经在打 `/metrics`，并且至少给 `cs_llm_not_ok_total`、外发失败、
   `/system/alerts` 配了告警规则。

## 5. 日常健康确认

| 想看什么 | 去哪里 |
|---|---|
| 进程活着 | `GET /health`（uptime） |
| 能不能服务 | `GET /ready`——库可查、迁移已跑、无致命安全项才算 ready；坏实例应从这里被摘掉 |
| 现在有什么要人看 | `GET /api/v1/system/alerts`（安全项、模型错误率、外发失败/死信、任务卡住、确认卡片超时） |
| 花了多少 token / 多少钱 / 哪个模型在失败 | `GET /api/v1/system/usage?days=7` 或设置页「模型用量」卡片 |
| 指标 | `GET /metrics`（Prometheus 文本；`cs_llm_*`、`cs_http_*`、`cs_mcp_pending_confirmations`、`cs_rate_limit_buckets`） |
| 后台任务归谁在做 | `GET /api/v1/system/status` 的 `leases`（holder + epoch） |
| 日志 | `src/backend/data/logs/cs_agent_<日期>.log`（按天滚动，保留 14 天）；容器里 `docker logs` |
| 向量库与 Chunk 表是否一致 | `python scripts/verify_restore.py`（只读对账），缺口大就 `--fix` 补建 |

## 6. 备份与恢复

```bash
cd src/backend
CS_CONFIG=config.local.yaml python scripts/backup_data.py --keep 7   # 快照 + manifest
python scripts/restore_data.py --list                                # 有哪些快照
python scripts/restore_data.py --snapshot <路径> --verify-only        # 核对清单，不动数据
python scripts/restore_data.py --snapshot <路径> --yes               # 真恢复
```

要点（都是踩过的坑）：

- SQLite 走 `sqlite3` 的 backup API，服务不用停也不能手抄 `.db` + `-wal`。
  `restore_data.py --verify-only` 会把"直接 cp 出来的残缺主文件"判死，别忽略它报的问题。
- MySQL 用 `mysqldump --single-transaction`、PostgreSQL 用 `pg_dump`；口令一律不放在
  命令行（同机用户 `ps` 就能看见）：MySQL 走 0600 的 `--defaults-extra-file`，
  PostgreSQL 走只注入子进程的 `PGPASSWORD`。
- **恢复不删东西**：现有 `data/<库文件>`、`chroma/`、`uploads/` 会被挪到
  `data/.restore-pre-<时间戳>/`，搞砸了能原样挪回来。
- 恢复脚本**不会**自动覆盖 `config.*.yaml`：快照里的配置是备份那台机器的路径与密钥。
- Chroma 是运行中拷出来的，索引可能撕裂；`Chunk` 表才是唯一真相，恢复后务必跑
  `verify_restore.py`，缺向量就 `--fix`。外部数据库的灌库命令脚本只打印不代做——
  覆盖别人的生产库是不可逆操作，必须人来执行。
- **多店时按店各留一份快照目录**：轮转是按目录算份数的，两个店往同一个 `--out` 里写会
  互相删对方的快照。定时化的写法见 `deploy/cs-backup@.service` / `.timer`（裸机）和
  `deploy/README.md` 第四节（容器 `compose run` + cron）。

## 7. 数据库迁移

两种模式，由 `database.migrate_mode` 决定：

- `auto`（默认）：`SQLModel.metadata.create_all` + `app/db/migrate.py` 的幂等补列。
  开发/小改好用，但**掩盖漏写迁移**：新列会被自动补上，谁也不会发现少了一个迁移。
- `alembic`：启动时 `alembic upgrade head`，跳过 `create_all`。生产建议切这个，
  漏写迁移会直接启动失败而不是静默补列。

```bash
cd src/backend
alembic revision --autogenerate -m "add xxx"   # 改完 models.py 之后
alembic upgrade head
alembic downgrade -1                           # 回滚一步（不可逆的迁移要单独评审）
```

新增列的兼容写法：先加**可空或有默认值**的列，别改既有列类型/约束；
需要重命名或改类型时，走"加新列 → 双写迁数据 → 切读 → 删旧列"四步，每步一个可回滚版本。

切到 `alembic` 时看库新旧，两条路不一样：

- **全新空库**：直接起服务，`upgrade head` 会把表建出来。**不要 stamp**——stamp 只写版本号不建表，
  stamp 完是个"自称已有结构"的空库，第一次用到就报 `no such table`。
- **以前用 `auto` 跑出来的存量库**：先 `alembic stamp 0001` 再改配置，否则 `upgrade` 会撞
  `table xxx already exists`。

```bash
# 存量库baseline（只打版本、不建表）
py -m alembic -c src/backend/alembic.ini stamp 0001
```

多店形态下这件事**按店各做一遍**：每个店是独立的 `database.url`，`upgrade head` 由各自的实例
在启动时自己跑（所以首启慢是正常现象，`TimeoutStartSec` / healthcheck 的 `start_period` 要留够）。

## 8. 容量与性能阈值（什么时候必须动架构）

| 信号 | 阈值 | 处置 |
|---|---|---|
| 店铺数 | > 1 | **一店一套实例 + 一店一个库 + 一店一套向量目录**（依据见 §1.1）。别在一个实例里塞多店：知识库没有 shop 维度，A 店的政策会答给 B 店的买家 |
| Postgres `max_connections` | 每进程上限 32（`pool_size=12 + max_overflow=20`，[app/db/session.py:42](../src/backend/app/db/session.py#L42)）×（店数 × 每店进程数） | 4 个店 × 1 进程就是 128，默认 100 会报 `too many connections`。要么调大 `max_connections`，要么把每店的 `pool_size` 压小，要么让店与店分库实例 |
| 在线会话数 | > 50 | 运营台 4s 轮询会放大读请求，上长连接推送替代轮询 |
| 知识库切片 | > 10k chunk | BM25 缓存要定期看命中率；再大建议换专职检索引擎 |
| SQLite 写入排队 | 单写者，三方并发（请求/sweeper/入库 worker） | 换 Postgres/MySQL，或减少副本。**多店形态必须 Postgres**（SQLite 文件按店分开也行，但备份/监控/连接管理都会变成 N 份手工活） |
| embedding 吞吐 | 批量上限 20、`rag.ingest_workers` 默认 2 | 大批量重入库放在低峰；换放行更高并发 embedding 的 key。**多店共用一个模型 key 时这条是全局的**：A 店在重入库，B 店的对话 embedding 一起排队 |
| 模型错误率 | `cs_llm_not_ok_total` 占比 > 10%（24h） | 先查 key 权限/限流，再配 `llm.fallback` 备用 provider |
| 限流放行量 | 每进程每键各算一份 | `CS_SERVER_WORKERS>1` 或同店多实例时，配置里的 `per_minute` 要按进程数除；否则整体放行量翻倍 |
| 反代 | SSE 逐字输出 | 每个店的 server 块都要写 `proxy_buffering off` + `proxy_read_timeout > llm.request_timeout_seconds`，漏写不报错，只是回答憋成整段（见 `deploy/nginx.shop.conf`） |

## 9. 回滚

- 应用回滚：镜像 tag 回上一个版本 → `docker compose up -d`。数据库结构**只往前滚**：
  回滚代码前先确认新迁移不是"破坏性"的（改列类型/删列），否则要么保留新列，
  要么用 §7 的四步法。
- 数据回滚：`restore_data.py --snapshot <时间点的快照> --yes`，恢复完跑
  `verify_restore.py --fix`。
- 配置回滚：`config.local.yaml` 的每次变更都要留版本（文件名带日期或进密钥管理系统），
  回滚 = 换文件 + 重启；`CS_CONFIG` 是整文件替换，不会与 `config.simple.yaml` 合并。

## 10. 已知没做的事（不要对客户承诺）

- 平台真实出站（淘宝/京东/拼多多/抖店）从未与官方联调过：参数字典是可配置骨架，
  ★ 项需在 readiness 里确认 `needs_review` 后逐条人工核对。
- 企微真实回调报文未与服务器对过（签名/加解密口径自洽，非联调结论）。
- 多租户（一个实例服务多个互不信任的商家）没有：RBAC 是 admin/staff/user 三档 +
  会话归属过滤，知识库与商品表仍是全局共享，隔离靠部署多套。
- 长连接推送：运营台仍靠轮询（`/metrics` 的 `cs_http_requests_*` 里能看到放大量）。
- 屏幕阅读器逐屏朗读、<400px 真机窄屏未做无障碍/兼容性验证。
